# 微信客户向自有 APP 迁移 · 转化链路设计

目标：把目前在微信/企微里用自然语言询价的钢贸客户，逐步迁到自有 APP 上自助询价下单，
同时**不打断现有成交**、**不激怒销售**。

---

## 一、先定第一原则：客户为什么要换

迁移失败最常见的原因是把它当成推广问题（"发个二维码让客户下载"），
而它其实是**产品价值问题**：APP 里必须有微信里给不了的东西，客户才会动。

钢贸场景下，微信的结构性缺陷和 APP 的可替代价值：

| 客户在微信里的真实痛点 | APP 能给什么 | 拉动力 |
| --- | --- | --- |
| 销售报的价是"某一刻"的，钢价一天几变，涨跌看不见 | 实时挂牌价 + 价格走势 | ★★★ |
| 想锁价要等销售回复确认 | 自助锁价（如 30 分钟窗口） | ★★★ |
| 问库存要等回，晚上没人回 | 自助查库存（规格/材质/产地/仓库） | ★★★ |
| 报价单散在聊天记录里，翻不到 | 报价历史可检索、可复用 | ★★ |
| 过磅单、质保书、发票混在聊天文件里 | 单据中心，按订单归档下载 | ★★★ |
| 对账靠销售发 Excel，来回核 | 在线对账 + 账期额度自助查 | ★★ |
| 重复采购要重新描述规格 | 一键复购上一单 | ★★ |

**最强的钩子是价格与单据**。钢贸客户对价格极敏感，"APP 下单专享价（每吨立减 X）"是转化率最高的单一手段；
而"过磅单/质保书随时能下载"是留存率最高的功能——它解决的是财务和质检的刚性麻烦。

反过来说，如果 APP 只是把微信聊天搬个壳，客户没有任何理由装。

## 二、五层漏斗：不要求客户一次跳变

直接从「微信聊天」跳到「APP 自助下单」，中间跨了下载、注册、学习三道坎，转化率会极低。
必须有中间层。**小程序就是那座桥**：在微信内、零安装、能承载结构化交互，而且能和 APP 共用账号与后端。

```
L0  微信/企微自然语言询价                     ← 现状，客户零改变
      │  销售在收件箱里把自然语言/图片/Excel 转成结构化询价单
      ▼
L1  小程序报价单（客户点开看、议价、确认）      ← 关键桥梁，零安装
      │  客户在小程序里留手机号（一键授权）
      ▼
L2  有账号的客户（手机号 + unionid）           ← 身份成型，可归因、可触达
      │  用 APP 独有能力（实时价/锁价/单据/对账）拉动
      ▼
L3  APP 安装并登录                            ← 手机号一键登录，无需重新注册
      │  首次 APP 下单给专享价
      ▼
L4  APP 内自助询价下单                        ← 终极目标
      │
      ▼
L5  微信降级为通知与客服兜底                   ← 永不关闭
```

### 核心机制：每一次微信询价都产出一张小程序报价单

这是整个设计的发动机。客户**不需要改变任何行为**（照旧在微信里发规格），
但每次都被动接触一次线上化体验。转化不靠说服，靠重复暴露。

对销售的要求也只有一条：**不要在微信里直接打字报价，要在收件箱里生成报价单再发出去**。
这一步必须让销售觉得更省事（自动带出库存价、历史成交价、自动算合计、自动生成 PDF），
否则他们会绕开。

### 关于 L5：微信永远不能关

一定有客户永远不装 APP——司机、仓管、年长的老板。
把"全部客户迁完"设成目标会导致对这部分客户的服务质量下降。合理目标是：
**让贡献 80% 交易额的客户迁移**，长尾留在微信。

## 三、身份链路（技术上最容易做错的一环）

### 已核实的平台约束

| 打通关系 | 官方机制 | 可行性 |
| --- | --- | --- |
| 小程序 ↔ 自有 APP | 绑到**同一个微信开放平台账号**，同一用户 unionid 唯一 | ✅ 确定可行，是官方设计的用法 |
| 微信用户 ↔ 企微 external_userid | `idconvert/unionid_to_external_userid` + `external_userid_to_pending_id` | ⚠️ **企业自建应用不可用**：官方文档写明该接口凭证只接受「第三方应用 access_token 或代开发应用 access_token」，且要求企微、开放平台、小程序**主体一致且均已认证** |
| 任意端 ↔ 任意端 | 手机号 | ✅ 无平台依赖，最可靠 |

**结论：不要把身份打通建立在 external_userid 转换接口上。** 走自建应用这条路它就是不可用的；
即使改走代开发/服务商路径，还要额外满足主体一致与认证要求，把架构押在上面风险太大。

### 设计选择：手机号为主键，unionid 为跨端补强

```
                        ┌─────────────────────────┐
                        │   Customer（主档）       │
                        │   customer_id           │
                        │   phone      ← 主键锚点  │
                        │   company_name          │
                        │   owner_sales_id ← 归属  │
                        │   price_tier  ← 客户分级 │
                        └───────────┬─────────────┘
             ┌──────────────────┬───┴──────────────┬──────────────────┐
             ▼                  ▼                  ▼                  ▼
    ┌────────────────┐ ┌────────────────┐ ┌────────────────┐ ┌────────────────┐
    │ wechat_identity│ │ app_identity   │ │ wecom_identity │ │ legacy_contact │
    │ unionid        │ │ app_user_id    │ │ external_userid│ │ 手机号/微信号   │
    │ openid(小程序) │ │ device_id      │ │ (人工或事件关联)│ │ 销售手工录入    │
    └────────────────┘ └────────────────┘ └────────────────┘ └────────────────┘
```

三条绑定路径，按可靠性排序：

1. **小程序留手机号**（主路径）：客户点开报价单 → 一键授权手机号 → 手机号 + unionid 同时拿到，
   `wechat_identity` 与 `Customer` 立即绑定。之后装 APP 用同一手机号登录，
   unionid 一致 → 自动识别为同一客户，**无需重新注册**。
2. **销售手工绑定**（兜底，覆盖长尾）：收件箱里给会话补填手机号。
   这条路径必不可少——很多老客户不会点小程序，但销售手上有他们的手机号。
   本系统现有的「设置发送目标」就是同类交互，可复用。
3. **企微客户事件关联**（可选增强）：若将来走代开发/服务商路径，再补 external_userid 自动关联。
   **不作为一期依赖。**

### 为什么手机号可靠

- 钢贸是 B2B，手机号本来就是必要信息（合同、发票、物流都要）
- APP 登录、小程序授权、企微客户资料三处都能拿到
- 客户换微信号的概率远低于换手机号，且换手机号会主动告知销售

## 四、询价单统一模型

无论从哪个入口进来，都落成同一个实体。这样"客户在 APP 里问的"和"客户在微信里问的"
才能进同一个池子、同一套报价流程、同一份历史。

```
Inquiry（询价单）
├─ inquiry_id
├─ customer_id            关联主档
├─ source                 wechat_chat | wecom_archive | miniprogram | app
├─ raw_content            客户原话/图片/Excel 的原始引用（可追溯）
├─ items[]                结构化明细
│   ├─ sku                品名（方管/热轧卷板/角钢…）
│   ├─ spec               规格（50*100*2.75）
│   ├─ material           材质（Q235B）
│   ├─ origin             产地/到站
│   ├─ weight_ton         吨位
│   └─ note
├─ status                 待报价 | 已报价 | 议价中 | 已成交 | 已过期
├─ owner_sales_id         归属销售（关键，见风险一节）
└─ trace_id               归因链路 ID

Quotation（报价单）
├─ quotation_id, inquiry_id
├─ items[] + unit_price + valid_until
├─ price_tier             按客户分级定的价（不是公开统一价）
├─ channel                发出渠道：miniprogram_card | pdf | app_push
└─ trace_id
```

**关键设计：`raw_content` 要保留客户原话的引用。** 钢贸的规格描述口语化、易歧义
（"方管 50 的"到底是 50*50 还是 50*100），结构化后必须能回溯原文核对，否则报错价的责任说不清。

## 五、归因链路：没有度量就没有迁移

每一个发给客户的链接都带 `trace_id`，贯穿整条漏斗。

```
trace = {
  trace_id,            一次转化尝试的唯一 ID
  customer_id,
  sales_id,            哪个销售发的（用于分销售看迁移率）
  inquiry_id,
  channel,             miniprogram_card | sms | pdf_footer | app_push
  created_at
}
```

埋点事件（最小集）：

| 事件 | 含义 | 对应漏斗层 |
| --- | --- | --- |
| `inquiry_created` | 收到询价（含 source） | L0 |
| `quotation_sent` | 结构化报价单发出 | L0→L1 |
| `quotation_opened` | 客户点开小程序报价单 | L1 |
| `quotation_negotiated` | 客户在小程序里议价/留言 | L1 |
| `phone_bound` | 客户授权手机号 | L2 |
| `app_installed` / `app_logged_in` | 装了并登录 | L3 |
| `app_inquiry_created` | 在 APP 里自助发起询价 | L4 |

### 指标定义（用来判断迁移是否真的在发生）

| 指标 | 公式 | 说明 |
| --- | --- | --- |
| **线上化率** | 产出结构化报价单的询价 / 全部询价 | 一期最该看的数。销售有没有真的改工作方式 |
| 报价单打开率 | `quotation_opened` / `quotation_sent` | 小程序体验是否够用 |
| 手机号留存率 | `phone_bound` 客户数 / 打开过报价单的客户数 | 身份成型速度 |
| APP 迁移率 | `app_logged_in` 客户数 / 有手机号的客户数 | L2→L3 转化 |
| **APP 自助询价占比** | `app_inquiry_created` / 全部 `inquiry_created` | **终极指标** |
| 分销售迁移率 | 按 `sales_id` 拆上面各项 | 用来发现谁在抵制 |

按交易额加权看，比按客户数看更有意义——迁走 10 个小客户不如迁走 1 个大客户。

## 六、分阶段落地（按依赖排序，不按日历）

### Phase 1 — 让每次微信询价都产出结构化报价单

这一期不需要 APP，甚至不需要小程序上线，价值就已经成立：销售报价效率提升 + 数据开始沉淀。

落点（在当前系统内）：
- 收件箱增加「把会话内容转成结构化询价单」：文字/图片/Excel → `Inquiry.items[]`，保留 `raw_content`
- 报价单生成：自动带出库存挂牌价、该客户历史成交价、上一单价格；算合计
- 输出两种载体：小程序卡片链接（带 `trace_id`）+ PDF（正式留档）
- 会话补填手机号，绑定 `Customer`
- 埋 `inquiry_created` / `quotation_sent`

依赖：无（当前收件箱已有会话、库存、历史价的雏形）

### Phase 2 — 小程序承接议价与身份

- 小程序报价单页：看明细、看单价、议价/留言、确认
- 一键授权手机号 → 绑定 `Customer` 与 `unionid`
- 报价历史列表（客户自己能翻到）
- 埋 `quotation_opened` / `quotation_negotiated` / `phone_bound`

依赖：小程序主体认证；绑定微信开放平台账号（为后续 APP 打通做准备，**这一步现在就要做**）

### Phase 3 — APP 上线，主打微信给不了的能力

优先级按第一节的拉动力排序：
1. 实时挂牌价 + 走势
2. 自助查库存
3. 单据中心（过磅单/质保书/发票）
4. 手机号一键登录（unionid 自动识别老客户）
5. **APP 下单专享价**（转化的主要经济激励）

依赖：APP 与小程序绑定同一开放平台账号；Phase 1/2 的数据沉淀

### Phase 4 — 自助闭环

- 自助锁价（短窗口 + 额度上限，见风险）
- 一键复购上一单
- 在线对账 + 账期额度
- 埋 `app_inquiry_created`

### Phase 5 — 微信降级

- 微信/企微保留为通知推送 + 客服兜底
- 大单、异常、议价仍走人工
- 长尾客户永久保留微信通道

## 七、风险与对策（按严重程度排序）

### 1. 销售抵制（最大风险，多数项目死在这里）

销售会担心：客户学会自助下单 → 我被绕过 → 业绩没了 → 所以我不推。
只要销售不推，L0→L1 这一步就断了，后面全塌。

对策必须是**机制性**的，不是号召：

- **归属不变**：APP 里客户永久绑定 `owner_sales_id`，客户在 APP 成交同样计入该销售业绩
- **迁移计入考核**：把"线上化率""分销售迁移率"作为过程指标纳入考核，而不是只考核成交额
- **让销售先受益**：Phase 1 的报价工具必须真的更省事（自动带价、自动算、自动出 PDF），
  让销售因为好用而用，而不是因为被要求而用
- **不砍人工议价**：大单、特殊账期、复杂规格仍必须走销售，APP 只接标准化重复采购

### 2. 价格透明化的副作用（钢贸特有的坑）

微信里一对一报价，客户之间看不到彼此价格。APP 上如果展示"统一价"，
不同客户的价差会立刻暴露，引发老客户质疑甚至纠纷。

对策：
- **不做公开统一价**，只做「该客户的专属价」（`price_tier` 驱动）
- 价格展示必须登录后可见
- 分级规则要能对客户解释得通（按年采购量/账期/回款表现），而不是随意定

### 3. 锁价的风险敞口

钢价波动大，客户锁价后价格上涨，公司承担价差。

对策：短窗口（如 30 分钟）、单客户额度上限、单日总量上限、
超限自动转人工确认；把锁价当成营销工具而非常态交易方式。

### 4. 身份打通失败

`external_userid ↔ unionid` 自建应用不可用（已核实）。若一期押在它上面会直接卡死。

对策：如第三节，**手机号为主键**，销售手工绑定作为兜底路径。

### 5. 结构化识别错误导致报错价

口语化规格识别成错的规格 → 报错价 → 客户按错价下单。

对策：`raw_content` 必须保留可回溯；报价单发出前销售必须**确认**结构化结果
（不做全自动报价）；报价单上标注有效期。

### 6. 部分客户永不迁移

接受它。不要为了迁移率牺牲这部分客户的服务体验。

## 八、一期建议的最小验证

不要一上来铺全量。选一个可控范围验证"漏斗是否真的漏得动"：

- 范围：1～2 个销售 + 他们的 20～30 个活跃客户
- 只做 Phase 1 + Phase 2 的报价单页与手机号绑定
- 观察两个数：**线上化率**（销售是否真的改了工作方式）、**报价单打开率**（客户是否愿意点）
- 判断标准：这两个数上不去，说明桥没搭对，不要急着投 APP 开发

APP 是重投入，应该在小程序这一层已经跑出正向数据之后再开工。

## 九、与当前系统的关系

现有统一收件箱是这条链路的**起点**，不是终点：

| 现有能力 | 在迁移链路里的角色 |
| --- | --- |
| 微信/企微消息统一收件箱 | L0 的承接面，销售在这里工作 |
| 会话「设置发送目标」交互 | 可复用为「补填手机号绑定客户」 |
| 库存查询、历史成交价、上一单 | 报价单自动带价的数据源 |
| 报价清单 + PDF 生成 | Phase 1 的报价单载体 |
| 运营台朋友圈/群发 | 迁移期的触达手段（推 APP 专享价活动） |

也就是说，Phase 1 主要是在现有系统上加「结构化询价单 + 归因 trace + 手机号绑定」，
不需要新建系统。

## 十、待确认事项

在动工前需要业务侧确认的几件事，会影响设计取舍：

1. 微信开放平台账号是否已有？小程序、APP、企微的**主体是否一致**（unionid 打通的前提）
2. 客户分级与专属价规则是否已有成文口径？（决定 APP 上价格怎么展示）
3. 销售考核是否愿意增加过程指标？（决定第 7.1 节的对策能不能落地）
4. 锁价是否被业务接受？可承受的价差敞口是多少？
5. 是否有代开发/服务商资质的可能？（决定 external_userid 自动关联要不要做）
